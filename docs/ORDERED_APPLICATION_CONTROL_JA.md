# 受付順に従うアプリケーション操作の共同署名

OCLOBなどのアプリケーションは、既存のFROST委員会で予約の取消にも署名できる。取消を支払証明に見せかけず、専用の `ApplicationControlVerifier` をプロセス内へ組み込む。

アプリケーション側の検証器は、各ノードが自分で保存した受付順、元の利用者の権限、先行約定の決済状況、DeFMIの現在の予約状態を確認する責任を持つ。検証器は汎用RPCから指定・呼出しできない。支払の検証器や試験用の健全性署名は変更しない。

署名基盤は操作IDと操作内容を暗号化された永続状態へ記録し、同じIDによる別操作への変更を拒否する。台帳上の無関係な更新に対応する再署名では親ルートだけを変更できるようにし、予約ID、消費順、直前の受領記録などは固定する。署名用の乱数を返す前に従来の一回限りの使用記録を保存する。再起動しても使用済みの乱数は再利用できない。

永続形式はV3。制御操作が存在しなかったV2だけは空の操作履歴を明示的に追加して読み込む。V3でこの履歴が欠落していれば読み込まない。既存の鍵や資金を初期化し直す変更ではない。

Softbankで `qomm-transport` の124テストと全対象の警告をエラー扱いするClippyを実行した。取消の利用者認証や実際の台帳解放はアプリケーション側の結合試験が別途必要であり、この検証器だけで安全な取消プロトコルが完成するわけではない。
